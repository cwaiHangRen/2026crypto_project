二、项目目标与范围

实现一个基于国密算法的“内容凭证 + 鲁棒水印”互补验证系统。

核心流程：
内容导入 → 分配 ContentID → 嵌入水印 → 生成最终发布文件
→ 计算 SM3 摘要 → 构造 Manifest → SM2 签名
→ 登记与发布 → 传播变换 → 恢复来源线索 → 联合验证。

系统需要支持：

（1）内容登记与发布；
（2）发布者密钥与信任配置；
（3）SM3 摘要和 SM2 签名；
（4）简化、版本化的 Manifest；
（5）承载 ContentID 的媒体水印；
（6）变换后水印检测与来源检索；
（7）父版本关系及授权派生；
（8）内容撤销、密钥撤销和版本状态检查；
（9）正常、合法编辑和攻击场景测试；
（10）四组方案对比；
（11）性能、存储开销与质量损失评测；
（12）适合匿名竞赛提交的代码、文档与运行证据。

必做媒体：
- 图片：至少支持 PNG、JPEG。
- 文档：首先实现 PDF，包括单页、多页、文字为主和图文混排文档。

扩展媒体：
- 音频、视频。
- DOCX 可作为后续导入或转换能力，不得把 DOCX 转为 PDF 后的支持写成对原始 DOCX 的完整水印支持。

默认要求：
- 普通 CPU 电脑可运行；
- 不依赖 GPU；
- 不依赖在线 AI 生成接口；

五、密码协议与发布顺序：必须先解决循环依赖

1. ContentID 与版本标识

- ContentID 表示某个已登记发布版本，而不是任意传播副本。
- 使用密码学安全随机源生成至少 128 位随机标识，并通过数据库唯一约束检测冲突。
- asset_id 表示同一作品的版本族。
- 每个经过授权、重新发布的版本分配新的 ContentID。
- 未重新签发的压缩、截图等传播副本，可能仍恢复出原版本 ContentID，但不能因此当作新的有效签名版本。
- 不要直接将“最终水印文件的摘要”用作必须提前嵌入的 ContentID，避免循环依赖。

2. 第一版采用独立 Manifest 文件

第一版采用“媒体文件 + sidecar Manifest + 本地登记库”。

正确顺序必须是：
a. 分配 ContentID；
b. 将 ContentID 等载荷嵌入媒体；
c. 完成编码、压缩和保存，得到最终发布文件；
d. 对最终发布文件的完整字节计算 SM3；
e. 构造 Manifest 的受保护正文；
f. 规范化序列化并签名；
g. 原子性登记发布文件与凭证。

禁止对嵌入水印前的文件签名，然后把嵌入水印后的文件当作同一个已签名文件。

签名后不得再修改发布文件。媒体文件和凭证导出打包不等于重新编码媒体。

后续若支持内嵌 Manifest，必须先定义明确的排除区间或容器绑定规则，并补充解析与篡改测试；不得临时跳过任意字节来让校验通过。

3. Manifest 正文

至少包含：

- schema_version；
- asset_id；
- content_id；
- version；
- publisher_id；
- signer_key_id；
- author_claim，可选，明确是声明；
- generator：工具名称、版本及生成方式声明；
- created_at：统一时间格式，注明是发布者声明时间；
- media_type；
- content_size；
- content_hash_alg；
- content_hash；
- metadata；
- metadata_hash；
- parent_content_id，根版本为 null；
- parent_manifest_hash，根版本为 null；
- transformation：本次授权派生操作及参数；
- allowed_transformations：允许变换的机器可读规则及范围；
- watermark_profile：算法、版本及必要的非秘密参数；
- signature_suite；
- sm2_user_id 或明确的协议固定标识规则。

全部会影响验证结论的字段，必须纳入签名保护。

Manifest envelope 可以包含：
- body；
- signature；
- 明确定义的签名编码字段；
- 受校验的辅助传输信息。

签名值本身不参与其自身待签名正文。

4. 规范化与摘要规则

- 采用明确、可测试的规范化序列化方案，优先使用 RFC 8785 JCS。
- 不得将“普通 json.dumps(sort_keys=True)”未经验证地称为完整 JCS。
- 拒绝重复 JSON 键、非法编码、NaN、Infinity、未知关键版本及歧义字段。
- 对整数范围、时间表示、null、空字段和未知字段制定规则。
- 不进行签名后隐式 Unicode 归一化或字段转换。
- 不用无长度边界的字符串拼接代替结构化编码。
- metadata_hash 对规范化元数据计算 SM3。
- content_hash 对最终发布文件完整字节计算 SM3。
- manifest_hash 对带固定协议域分离前缀的规范化 body 计算 SM3。
- parent_manifest_hash 引用这一明确的正文摘要，并在验证时同时验证父凭证签名。

5. SM2 签名

优先使用“SM2-with-SM3 对明确消息字节签名”的高层接口。

待签名消息采用：
固定协议域分离前缀 || canonical_body_bytes。

- 明确 SM2 用户标识的实际字节和长度。
- 明确 ZA 由哪一层生成。
- 明确库接口接收消息还是预计算摘要。
- 不得因接口误解而省略 ZA，或无说明地重复摘要。
- 明确公钥格式与签名格式，例如 DER 签名编码。
- 不自创 SM2、SM3 算法。
- 不使用 ECDSA、SHA-256、HMAC 或 mock 冒充 SM2、SM3。
- 不固定签名随机数，不使用普通随机数生成器生成私钥或签名临时值。
- 固定密钥仅用于标明用途的测试向量。

至少提供：
SM3 已知答案测试、SM2 正常签验、错误消息、错误公钥、错误用户标识、签名损坏和跨实现验证测试。

六、密钥、信任、版本和撤销

1. 密钥与信任

- 支持生成密钥、导入公钥、查询 key_id、配置发布者信任关系。
- key_id 使用明确编码的公钥摘要，不依赖文件名。
- 验证器只需要公钥，不得调用发布者私钥完成验证。
- 不自动信任 Manifest 自带的公钥或自称的作者姓名。
- 分别记录 signature_valid 和 issuer_trusted。
- 第一版使用本地受信公钥清单，不必建设完整 CA。
- 私钥不得进入日志、测试结果、匿名提交包或版本库。
- 演示私钥与真实使用密钥分离。
- 私钥保护采用成熟方案，不自创加密格式；明确本地文件权限和剩余风险。
- 内容签名密钥与登记服务状态签名密钥分离。

2. 版本链

第一版优先实现单父节点的线性版本链：

- 子版本签名绑定父 ContentID 与父 Manifest 摘要；
- 验证父节点存在、正文摘要、签名、版本号、asset_id 和授权关系；
- 第一版可限定同一发布者创建派生版本；跨发布者协作留作显式授权扩展；
- 检测断链、父节点替换、跨作品串链、重复标识、循环关系；
- 限制链深度和解析资源；
- 登记库维护每个 asset_id 的当前版本状态。

仅有 ParentID 字段不算实现了可验证版本链。

3. 授权编辑

区分：

A. 未重新签发的传播变换：
压缩、裁剪、截图等发生后，旧凭证可能仍可恢复，但当前文件的硬绑定通常不再匹配。

B. 经过授权的编辑发布：
授权操作生成新文件、新 ContentID、新 Manifest 和新签名，并绑定父版本。

“allowed_transformations 包含某操作”不等于系统已经证明当前文件确实仅发生了该操作。

除非实现了额外、可验证的变换证明，否则不得将任意摘要不匹配文件自动认定为合法派生。

4. 撤销与状态新鲜度

- 区分内容撤销和签名密钥撤销。
- 撤销记录包含目标、原因、时间、签发者和状态序号，并具有可验证的授权。
- 当前版本及撤销状态通过可信登记服务查询，或通过签名状态快照提供。
- 状态快照需要定义序号、签发时间、有效期和新鲜度规则。
- 客户端保存已接受状态序号的高水位，拒绝已知回退。
- 必须说明：仅有签名不能保证状态是最新的；离线且缺少可信新鲜状态时，应返回未知或过期，而不是“未撤销”。
- 不能声称本地数据库天然防篡改，或一个签名快照天然防止首次使用时的旧状态重放。
- 普通系统时间不是可信时间戳，不能凭自填时间证明内容在密钥撤销前已合法签发。

“父版本回滚”测试必须区分：
- 合法历史版本被正常查看；
- 旧版本冒充当前最新版本；
- 凭证中的父关系被篡改。

合法历史版本不是天然攻击。要求“最新版本”的验证模式才应依据可信状态拒绝旧版本冒充当前版本。

七、水印实现与文档适配

1. 水印的职责

水印用于恢复 ContentID 等来源检索线索，不单独提供内容完整性或作者身份保证。

要求真正修改媒体内容的可感知信号：
- 不能仅写 EXIF、文件名、PDF 属性或自定义元数据；
- 不能只在数据库保存 ContentID，却把查询结果当作水印识别；
- 不能把简单可见文字或二维码当作鲁棒隐形水印的全部实现。

可见二维码或标识可作为独立展示功能，不计入隐形水印主指标。

2. 图片水印

先实现一个能在普通 CPU 上运行的真实基线，例如：
- 变换域嵌入；
- 分块和空间冗余；
- BCH 或 Reed–Solomon 等纠错；
- 必要的同步、尺度或位置恢复策略。

具体路线由你通过小规模实验选择，不要未经验证承诺裁剪、截图后达到 95%。

载荷至少包含：
- 协议版本；
- ContentID；
- 必要的载荷校验与纠错信息。

说明有效载荷长度、纠错冗余、重复次数、嵌入强度、支持尺寸和检测开销。

CRC 只能用于检测传输错误，不能描述为抗伪造的密码认证。

检测接口不得要求原始未水印图片或真实 ContentID。算法需要的密钥、公共配置和候选搜索范围必须公开说明。

如果使用开源水印实现：
- 保留许可证与来源；
- 说明哪些代码复用、哪些由本项目实现；
- 对实际鲁棒性进行独立测试；
- 不将调用第三方库包装成“自主发明水印算法”。

3. PDF 文档

- 水印必须进入页面渲染内容，使页面截图有机会保留来源线索。
- 首先实现明确的 PDF 支持范围，再逐步扩展。
- 记录页面数、渲染 DPI、嵌入方式、页面标识和检测范围。
- 测试文字页、图文页、多页文档以及页面截图。
- 若采用栅格化发布，明确说明文字可搜索性、可编辑性、清晰度和文件体积的变化。
- 不得把失去文字层的结果描述为完全保留原文档功能。
- PDF 某页截图识别成功，只能报告该页或区域的来源线索，不能声称整份文档完整性通过。
- 测试删页、换页、页面重排、页面拼接和局部截图。
- 记录多页出现不同 ContentID 或多个候选时的冲突，不得静默选择一个并显示“通过”。

4. 必须公开的水印边界

- 水印可能被删除、损坏或复制；
- 把合法水印复制到其他内容上，并不会赋予该内容有效的硬绑定；
- 不能仅凭“恢复出已登记 ContentID”就显示“来源可信、内容未篡改”；
- 相似度、指纹或语义比较如被引入，只能作为另列的辅助信号；
- 不得把相似度阈值结果描述为密码学证明。

八、验证器与结果语义

实现分层验证，不允许只返回一个 true/false。

至少返回以下维度：

- manifest_presence；
- manifest_schema；
- signature_valid；
- issuer_trusted；
- content_hash_match；
- watermark_status；
- recovered_content_ids；
- parent_chain_status；
- authorization_status；
- content_revocation_status；
- key_revocation_status；
- state_freshness；
- latest_version_status；
- checked_scope：整份文件、页面或区域；
- reasons；
- timings。

每个维度支持适当的 PASS、FAIL、UNKNOWN、NOT_CHECKED、NOT_APPLICABLE 状态，而不是把所有未知都归为通过或攻击。

总体结论至少区分：

1. VERIFIED_EXACT
   当前文件与受信发布者的有效凭证精确绑定，适用的状态检查满足要求。

2. VERIFIED_DERIVATIVE
   当前文件具有新的有效签名，且父版本关系和编辑授权通过。

3. ORIGIN_HINT_ONLY
   恢复了来源线索，但当前文件没有通过相应的精确内容绑定。

4. REJECTED
   存在明确违反验证策略的证据，附具体原因。

5. INDETERMINATE
   因状态不可用、链不完整、证据冲突等原因无法作出充分判断。

6. NO_PROVENANCE
   没有找到可用来源凭证，不代表内容一定恶意或一定不是 AI 生成。

必须保留以下语义：

- 摘要不匹配 ≠ 已证明发生恶意篡改；
- 无水印 ≠ 内容伪造；
- 签名有效 ≠ 发布者已受信；
- 恢复 ContentID ≠ 当前文件完整性有效；
- 当前状态未知 ≠ 未撤销；
- 旧版本 ≠ 伪造版本；
- 系统错误或超时 ≠ 成功检测攻击。

提供明确的验证模式：
- hard：已定位凭证后的精确硬绑定验证；
- recover：丢失凭证后的水印恢复与联合检查；
- full：执行所声明的完整验证流程。

未执行的检查必须显示 NOT_CHECKED，不能在界面上暗示已经全部验证。

九、核心功能与演示界面

提供可脚本调用的 CLI，并在其上复用服务层实现 API 和 Web 页面。

CLI 功能至少包括：

- doctor：检查环境和依赖能力；
- keygen：生成演示密钥；
- trust：管理本地受信公钥；
- register：登记并发布内容；
- verify：验证文件；
- transform：执行预定义传播变换；
- derive：授权编辑并签发新版本；
- revoke：撤销内容或密钥；
- history：查看版本链；
- benchmark：运行固定评测；
- demo：运行小规模端到端演示；
- export：导出结果与匿名提交材料。

命令名称可以调整，但必须提供真实可运行的等价能力。

中文演示界面至少包含：

- 内容登记与发布；
- 文件验证；
- 传播变换前后对比；
- 版本链和撤销状态；
- 四组方案测试结果。

界面必须展示真实后端输出，不使用写死的识别成功率、延迟或签验结果。

所有关键操作保留结构化日志，但不得记录私钥、秘密口令或参赛人员身份信息。

十、四组对照实验

实现统一实验接口，比较：

G0：无凭证、无水印；
G1：仅签名凭证；
G2：仅水印；
G3：水印 + 签名凭证 + 版本链 + 撤销状态。

要求：

- 使用相同基础内容、变换参数和计时环境；
- G2 与 G3 尽可能使用相同水印算法及强度；
- 区分“来源线索恢复能力”“内容完整性验证能力”“版本和撤销判断能力”；
- 不适用的功能标记 N/A，不能伪造支持；
- 没有凭证的组不能因为无法验证就显示“验证成功”；
- 不允许测试程序把真实 ContentID、攻击标签、原文件路径等答案泄漏给检测器；
- 真值由评测器保存，检测器只能访问真实部署时可获得的输入；
- 记录仅签名方案在元数据或 sidecar 丢失时采用了何种检索能力，保证比较口径透明。

可增加子消融实验，但不得替代上述四组。

十一、数据集、变换和质量评测

1. 数据集

建立固定、可复现的数据集清单和生成或导入脚本。

完整评测支持不少于 1000 个基础样本，图片和文档都必须有实质性样本覆盖。可先按 600 个图片、400 个文档规划，并根据实际数据条件记录调整。

分别报告：
- 基础文件数；
- 不同内容来源数；
- 变换实例数；
- 正常、合法编辑和攻击用例数；
- 各媒体类型数量。

不得用少量原图的重复压缩结果冒充大量独立基础内容。

先建立小型 fixtures 跑通系统，再扩展完整测试。

数据要求：
- 记录来源、授权情况和生成方式；
- 合成测试图可以用于机制和工程测试，但不能冒充真实 AI 生成内容数据集；
- 缺少真实数据时，保留导入接口并明确评测代表性限制；
- 不使用真实参赛者个人信息生成示例；
- 按基础内容来源拆分开发、调参与冻结测试集，同源变体不得跨集合泄漏；
- 测试集、参数和阈值冻结后不得为提高成绩反复针对测试集调参；
- 固定变换随机种子，但不因此固定生产签名随机数或生产 ContentID。

2. 变换配置

将参数保存到 configs/attacks.yaml 或等价配置文件。

图片与文档至少覆盖：
- JPEG 压缩；
- 尺寸变化；
- 轻度裁剪；
- 截图；
- 格式转换；
- 元数据清除；
- PDF 页面重新渲染；
- 多步组合变换。

参数必须量化，例如 JPEG 质量、缩放比例、裁剪保留面积、截图视口和文档 DPI。

开发阶段可从 JPEG 质量 90/75/50、缩放比例 0.5/0.75/1.5、裁剪保留面积 95%/90% 等参数起步；这些只是初始评测配置，不是达标承诺。

明确区分：
- 承诺支持范围内的正常变换；
- 边界压力测试；
- 超范围破坏性变换。

在测试前固定范围，不能测试失败后再把样本划为“不支持”。

“截图”必须说明：
- 是实际浏览器或阅读器截图；
- 还是渲染、缩放和编码形成的模拟截图。

没有真实截图实验时，不得将模拟截图结果写成真实截图结果。

音视频扩展后增加：
- 音频重采样、编码压缩；
- 视频转码、分辨率和帧率变化。

3. 水印质量

同时记录：
- 图片 PSNR、SSIM 或其他明确解释的质量指标；
- 文档可读性与页面效果样例；
- 文字层和可搜索性是否保留；
- 水印有效载荷与编码后位数；
- 水印强度和文件大小增量。

不能通过明显破坏内容质量、添加巨大可见标识来“实现”鲁棒性目标。

十二、安全测试与攻击检测口径

至少实现以下攻击：

1. 内容替换，但继续携带原凭证；
2. 媒体局部修改；
3. Manifest 字段篡改；
4. 签名字节篡改；
5. 错误公钥验证；
6. 攻击者自建密钥冒充受信发布者；
7. 修改 ContentID、publisher_id、allowed_transformations；
8. 父版本替换、断链、跨作品串链；
9. 旧版本冒充最新版本；
10. 已撤销内容复用；
11. 已撤销密钥继续签发；
12. 旧状态快照重放；
13. 水印复制到无关内容；
14. 多个水印或多个候选凭证冲突；
15. PDF 页面替换、删除和重排；
16. 重复 JSON 键、异常字段、畸形编码；
17. 超大文件、异常压缩包结构或渲染资源消耗；
18. 不受信输入中的外部地址和路径注入。

所有攻击仅在本地测试数据与明确授权的测试环境中执行。

检测指标必须分开：

A. 摘要与签名层：
内容替换、Manifest 篡改、签名损坏、错误公钥等，要求定义的负例全部被正确拒绝。

B. 版本、授权和状态层：
回滚、撤销复用、状态重放等，依据相应可信状态和策略检测，不归功于文件摘要本身。

“100%”仅表示冻结测试集和明确威胁模型下全部用例被正确处理，不表示证明所有未来攻击都能被检测。

每个攻击用例必须定义：
输入变化、攻击者已知信息、预期检查层、预期状态、实际状态、是否正确处理。

不得以程序崩溃、解析器超时或一律拒绝所有文件来提高攻击检测率。

特别注意：
如果攻击者把文件和凭证一起换成另一份完全合法内容，识别这种替换需要可信的预期 ContentID、作品或发布者约束。
没有这类外部上下文时，不得声称系统能区分“用户原本想验证的内容”和“另一份合法内容”。

十三、性能目标与统计规则

目标：
- 预定义支持范围内，整体 ContentID 正确识别率不低于 95%；
- 定义的摘要/签名攻击与有状态攻击用例，正确检测目标分别为 100%；
- 图片和文档单文件验证 P95 延迟目标不超过 100 ms；
- 所有结论最终以实测为准。

统计要求：

1. 水印识别率以完整 ContentID 正确恢复为成功，不以“检测到某种水印信号”代替。
2. 分媒体、分变换、分强度报告样本量和结果。
3. 同时报告微平均和宏平均，不能用大量容易样本掩盖难项失败。
4. 嵌入失败、解码失败、超时、错误 ContentID 和多候选冲突单独计数。
5. 在预先声明支持范围内的失败不得从主指标分母中偷偷删除。
6. 单独报告无水印样本误检率、错误 ContentID 接受率、合法编辑误判率和正常文件误拒率。
7. 报告均值、P50、P95、批量吞吐量及失败请求情况。
8. 记录 CPU、内存、操作系统、依赖版本、文件大小、图像分辨率、PDF 页数和渲染 DPI。
9. 分别计时读取、摘要、签名验证、水印检测、凭证查询、链检查和撤销检查。
10. 分开报告 hard、recover、full 三条路径，不能用快速摘要路径代替完整水印恢复路径证明达标。
11. 多页 PDF 不得只验首页却以整份文档名义报告延迟。
12. 说明进程启动、文件 I/O、缓存、PDF 渲染、数据库查询和网络等待是否包含在计时中。
13. 声明单文件 P95 达标时，必须给出对应媒体规模和测量边界。
14. 同时报告 Manifest 字节数、媒体文件增量、水印载荷/冗余和登记库开销。
15. 检测阈值只能在开发/验证集确定。
16. 未达 95% 或 100 ms 时，保留原始结果，分析原因并提出后续实验；不得修改统计口径来掩盖问题。

结果至少输出：
- 逐样本 JSONL 或 CSV；
- 汇总 JSON；
- 可阅读的 Markdown 或 HTML 报告；
- 失败样本索引；
- 运行配置、随机种子和代码版本信息。

报告中“目标值”和“实测值”必须分栏展示。

十四、基础工程安全

- 默认仅监听本机回环地址；
- 写操作具有明确授权，不能因为是演示页面就允许任意撤销或签发；

- 不自动访问 Manifest 中任意 URL，优先使用本地登记库；

- 调用外部程序不得拼接 shell 命令；
- 数据库写入使用事务，保证同一 ContentID 不映射到不同正文；
- 保存与签名之间注意文件被替换的竞态问题；
- 测试框架与生产验证逻辑分离，测试真值不能参与业务判断。
